# DISC2 release and recovery on IIS

Keep the previous code, its external configuration, its IIS application settings and the database online-backup procedure available throughout the cutover. Rehearse on IIS staging using synthetic records and a non-production BMA endpoint. Record the tested versions, package digest, operator, backup location and results in the private change record.

## Build and verify

Use a reviewed checkout and an annotated OpenPGP-signed version tag. Obtain the approved primary or signing-key fingerprint through the release approval channel. The builder needs Git with GPG, Composer 2, PHP 8.2 or later, ext-zip, PDO SQLite, cURL, iconv, intl, mbstring, sessions, XML and OPcache. Use an NTFS or Linux filesystem with hard-link support for the output directory. Keep PHP, Composer, libzip, zlib, Git and timezone fixed across reproducibility comparisons. The installer downloads the distribution files pinned in `composer.lock`.

```powershell
.\tools\release.ps1 -Tag $tag -SignerFingerprint $approvedFingerprint -Output D:\releases\disc2.zip
.\tools\verify-release.ps1 -Archive D:\releases\disc2.zip -ExpectedSha256 $approvedDigest
```

Record the SHA-256 reported by the build with the signed tag and commit. Transfer the ZIP to staging and independently obtain `$approvedDigest` from the build record. Run the verifier from the reviewed checkout. It checks the whole-file digest, entry types, package allowlist, production dependency versions/references and every payload digest in `release-manifest.json`. The builder also writes `disc2.zip.sha256`. Both commands run through PHP CLI, and the build accepts `-ComposerPhar` for a custom Composer installation.

The builder archives the signed commit into a new directory, installs the production class map and checks PHP platform requirements. It reopens the finished ZIP and boots its extracted production runtime for container validation, route checks and cache warmup. The calendar ships with the pinned upstream flatpickr 4.6.13 CSS, JavaScript and Thai locale. Check the distribution digests in the release tests and retain its packaged MIT license. [Upstream distribution](https://www.npmjs.com/package/flatpickr/v/4.6.13)

Keep the ZIP intact until verification. Extract into an empty release directory. Keep old and new code in separate directories to prevent leftover procedural files.

## Stage the IIS application

1. Block public traffic and all application/background writes while the previous release is still active. Block sign-ins, drain active transactions and record the UTC freeze time. Export the original IIS mapping and settings, including the physical path, bindings, handlers and app-pool identity. Save a private copy of the previous external configuration and verify its SHA-256 against the original. Record its restore location and the retained prior package. If the previous deployment uses the optional AI PHP configuration, snapshot that file separately, verify its SHA-256 against the original and retain its selected path for recovery.
2. Record the authoritative database path and run `SELECT COALESCE(MAX(id),0) FROM uat_audit_log` on the frozen database (use zero if the ledger does not exist). Use the SQLite CLI `.backup` to take a fresh protected online backup including committed WAL data. Open it independently and verify the same audit watermark, exactly `ok` from `PRAGMA integrity_check` and zero rows from `PRAGMA foreign_key_check`. Record the backup's location and SHA-256. **Pre-switch gate:** record both completed steps before changing the mapping or external config, running migration or testing a login. An incomplete baseline keeps the previous mapping in place and staging frozen.
3. Configure IIS application `/exam/disc2` on the intended site and HTTPS binding. Use `C:\inetpub\wwwroot\exam\disc2\public` as its physical path. Install IIS URL Rewrite and configure PHP FastCGI with `php-cgi.exe`. Use the `php.exe` from that installation for CLI commands. Configure anonymous authentication to use the application-pool identity. Ensure the site denies direct access to other release trees and private storage from every binding.
4. Set `APP_ENV=prod`, `APP_DEBUG=0`, a private `APP_SECRET` and the same `DISC2_CONFIG_FILE` in FastCGI and the operator CLI. Configure `super_admin_ids`, `bma_secret_key` and an absolute `database_path` in the private PHP config. On staging, set `bma_endpoint` to the approved non-production HTTPS directory URL and use its matching staging key. The released code accepts an absolute HTTPS URL without user information or fragment and validates the TLS peer. Redirects stay on the configured origin. Production deployments that omit this key use `https://register.bangkok.go.th/bmamailadmin/web/index.php?r=api/getuserinfo`. Obtain the expected URL independently from the change record. Keep the staging site isolated until the preflight confirms it points to the approved non-production host. Store the SQLite database, WAL/SHM and backups outside the release and web-accessible locations.
   Set `trusted_hosts` in the external PHP array to the exact DNS names or IP literals served by this binding, for example `['disc-stage.example']`. Direct IIS uses an empty `trusted_proxies` list by default and the socket peer for login limits. Behind an approved reverse proxy, list only its IP addresses or bounded CIDR ranges, for example `['192.0.2.10']`. Restrict direct access to that proxy and configure it to replace incoming forwarding headers. Symfony uses `X-Forwarded-For` for the client IP and `X-Forwarded-Proto` for HTTPS only from those peers. Host validation always uses the request Host.

   If using the optional AI gateway, select the same absolute `DISC2_AI_CONFIG_FILE` in the IIS FastCGI settings and operator CLI, or use the existing default `C:\inetpub\private\disc2-ai.php`. Store a byte-identical independent recovery file in operator-controlled private storage outside the release and SQLite tree. Verify its digest before the switch and supply its absolute path as `-AiConfigBackup` on every smoke run. With no setting and no default file, the gateway and this recovery parameter are optional. The smoke checks the binding's FastCGI/pool/machine selection, reads effective pool rights on the selected file, parent and every ancestor, and verifies recovery bytes before migration. Record the active paths and digests privately.

5. Grant the pool read/execute across source, vendor, tools and the config file. Create `var`, `var\cache`, `var\log` and `var\sessions` under the extracted release. Grant Modify on those three writable subdirectories and on the database and its dedicated parent for SQLite sidecars. Use separate private directory trees for configuration and data, for example `C:\inetpub\private\disc2-config.php` and `D:\disc2-data\disc_uat.db`. Supply their direct paths for ACL validation. The pool needs read rights on both the config file and its immediate directory. Reserve delete, delete-child, data write, owner and ACL changes there for administrators. Grant Create files and Delete subfolders and files on the dedicated database directory so SQLite can create and delete sidecars. Grant inherited Modify on data files including existing WAL and SHM. The gate checks effective rights on every configuration ancestor through the volume or share root before loading the PHP config. Reserve delete, delete-child, change-owner and change-permissions rights along that chain for administrators. An unreadable or unidentified AccessChk result blocks staging. Install Microsoft's AccessChk in the operator's PATH and accept its license on staging. The smoke script reads the pool identity and checks effective rights. [AccessChk documentation](https://learn.microsoft.com/en-us/sysinternals/downloads/accesschk)

```powershell
# Run on the isolated IIS staging site or during the approved production freeze.
$smoke = @{Site=$site; BaseUri=$httpsUrl; ExpectedBmaEndpoint=$approvedBmaUrl; ConfigFile=$configFile; Database=$database; Php=$phpExe}
# If AI is configured, add its independently verified protected copy.
if ($aiRecoveryCopy) { $smoke.AiConfigBackup = $aiRecoveryCopy }
.\tools\iis-smoke.ps1 @smoke -ApplyMigrations
```

For an approved production run add `-Production` and supply the approved production BMA URL. The default staging gate rejects the production directory hostname. The script selects HTTPS bindings of started IIS sites and requires the requested site to be started. Before loading the external PHP config or opening SQLite, it probes the selected live HTTPS listener and compares all seven static asset digests (including the pinned calendar, stylesheet and Thai locale) against the release manifest. It confirms the site is still started immediately before running the migration. It pins the HTTPS probes to that selected local address, bypasses proxies, and validates the original TLS hostname.

The explicit switch runs `bin/console app:migrate --env=prod --no-debug` after confirming the selected external database. The command checks the migration ledger, SQLite integrity and foreign keys. Subsequent smoke runs can omit the switch. The script checks PHP and FastCGI modules, pool access, the mounted login and protected URL, cookie scope, session-backed CSRF across requests, static file digests and private-path denials. Validate the actual HTTPS response through the intended binding. In IIS Manager confirm the running FastCGI application's environment and loaded php.ini correspond to the checked CLI/CGI configuration. Verify local Admin and staging BMA authentication, case list/detail, workflow tabs and scoped audit reads with approved identities. Exercise two concurrent synthetic sessions on staging. Record their writes and audits before the rollback rehearsal. Keep production writes frozen until the operator signs off. Users sign in again and reopen forms after switching code.

## Production rollback preserves the current database

1. Freeze all writers again. Retain the current database at its authoritative path. Take a **new SQLite online backup of the current database** after the last write. Validate integrity, foreign keys and SHA-256. Protect this rollback-time snapshot separately from the pre-cutover backup. Record the case, workflow, assignment and audit IDs changed since cutover in the private change record.
2. Switch to the retained previous code and compatible machine configuration, including the verified optional AI copy and its selection when applicable. Restore its original IIS physical path, rewrite/handler settings and app-pool identity. Keep the service behind the traffic block during validation. The previous procedural release opens `data\disc_uat.db` relative to its own directory. Rehearse mapping that path to the retained authoritative file, for example with a private data-directory junction to dedicated storage. Verify volume and file ID via `fsutil file queryfileid` on both paths and confirm all database/sidecar URLs are denied by IIS. Preserve the live WAL and SHM alongside the database. Recycle the pool to clear stale opcode and session state.
3. Use the verified Symfony package's `tools\rollback-proof.php` outside the restored webroot. Supply the **rollback-time** backup and the recorded pre-cutover maximum audit ID. The tool opens the current database via the previous code's actual `db.php`, compares every table, index, trigger and view definition, then every stored row including the audit ledger against that frozen backup, and reports the post-cutover audit count. Require a zero exit status and the expected audit count. During rehearsal require at least one new audit row.

   ```powershell
   & $phpExe D:\releases\verified-symfony\tools\rollback-proof.php $priorRelease $rollbackTimeBackup $preCutoverAuditId
   if ($LASTEXITCODE -ne 0) { throw 'Keep writes frozen' }
   ```

4. Through the old IIS application, sign in again and open the affected cases, outcomes, assignments and audits using the appropriate roles. Reconcile all recorded post-cutover IDs and values. Confirm this release's access controls and database-file denials. If any comparison, route or permission fails, keep writes frozen and retain both current database and rollback-time backup for forward recovery. Reopen only after the operator records all results. The pre-cutover snapshot is never restored over production writes.

Keep SQLite sidecars from the prior live directory separate. Point the previous code at the restored demo file, run integrity and foreign-key checks, sign in and verify pre-cutover cases and audit counts.
